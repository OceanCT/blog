# Note

将本次学习中值得保留的理解整理为可回看的博客文章，并实际写入博客仓库、生成可浏览的预览页面。默认先审阅，用户确认当前版本没有问题后，自动完成 GitHub 源码更新与站点发布，不再另问一次是否推送。默认中文，保留准确的术语、代码和公式。不要把仅创建 skill 的请求当成写文章请求。

## 找到博客

默认本地仓库 `/Users/oceanct/projects/blog`，远端 `https://github.com/OceanCT/blog.git`。用户指定的路径优先。先检查 `git status --short`、`git remote -v`、仓库中的 AGENTS.md 和 `_config.yml`。路径不存在时克隆到用户可写的目录，不在其他项目里初始化博客。保留已有未提交修改，不自动 reset、stash 或切换覆盖工作。

博客采用 Hexo，主题 `themes/ocean`，内容在 `source/_posts/*.md`，发布地址 `https://oceanct.github.io/blog/`。`legacy/posts` 是退出展示的历史内容，不自动搬回博客。不要编辑 `public` 来创作文章，它由构建生成。

## 整理内容

从用户本轮材料和已讨论的结论提炼主题。已有足够信息时直接写；只有缺少笔记主题或原始内容时才追问。不要用样例、占位文本或自行选择的主题填充博客。

文章面向以后回看学习过程的自己，也让读者能跟着理解。开头从正在讨论的问题进入，有必要时交代学习背景；已经形成的理解自然展开，仍待研究的问题如实保留。选材优先保留：

- 怎么做：实际采取的步骤、实现机制、关键代码或推导，以及验证结果。
- 为什么这么做：选择依据、约束、权衡，以及讨论过且影响理解的其他方案。
- 集中询问的问题：归并反复追问的概念、误解和边界，用连贯解释给出最终答案。
- 难点：卡在哪里、如何定位或想通、哪些问题仍未解决。

以上是选材重点，不是每篇必须使用的四个标题。根据主题组织成连贯文章，合并重复追问，排除无关分支；短记录可以只有几段。对话没有提供的实践、选择理由或验证结果不得补写成既成事实。确有必要补充的解释应与本次实践区分并附依据。避免聊天逐字稿、过程播报、空泛总结和虚构的第一人称经历。

保留推导所需前提、张量形状、命令参数或版本条件；区分材料提供的事实、自己的推断和待验证问题。外部资料附原始链接，不编造引用或测试结果。用户给出的链接先读取；无法访问时明确说明证据缺口。处理代码块和数学表达式后检查实际 HTML，不能假定主题支持公式排版。发布前移除与主题无关的私人信息和凭据。

先搜索 `source/_posts`，主题重复时根据用户意图补充已有文章；修改已有文章保留 `date` 与文件名，填写 `updated`。新笔记使用简短的英文 kebab-case slug、真实当前日期、1 到 4 个相关标签和一句具体摘要。

新建笔记时同步维护博客 `source/_data/columns.yml`，将文章 slug 加入所属主题并按学习逻辑安排顺序。首页与专栏按主题和阅读顺序组织，归档保留时间顺序；站内“专栏”链接指向 `/blog/columns/<id>/`，不使用按时间排序的标签页代替专栏。

## 文章边界与结束位置

动笔前明确本篇要让读者理解的核心问题。补充内容用于补齐理解这个问题所需的前提、机制和边界；核心问题已讲清时就结束，不因相关话题还能展开而追加实现路线、后续计划或另一篇教程。判断是否拆篇，看读者是否已经从“理解这个系统”转向“实现一个系统”等新的任务，而不是只看篇幅。介绍文章中的必要调用示例可以保留；完整动手实现、实验过程和项目复盘通常另成一篇。尚未开展的实践留在内部计划中，等有实际过程与结果后再写，不为它提前创建占位文章。用户明确要求原理与实践合讲时，按其范围组织。

## 读者与内容取舍

介绍个人工具或 skill 时，保留简短、有个人语气的背景，再给下载入口，重点解释观察到了什么问题、为什么选择这些规则，以及怎样使用。先从用户样稿与实际生成文本的具体差异提炼原因，避免把个人阅读偏好写成对所有 AI 或所有人的普遍结论。讲解逻辑与表达风格可以分开讨论，不把规则逐条复述成正文。

完整实现放附件或独立副本，正文只选有解释价值的重点。操作型教程按读者实际执行顺序展开，交代命令的输入、产生的对象或状态、观察方式，以及下一步为何能继续。自写初始化或验证脚本若封装了理解主线必需的步骤，应在正文展示入口代码或关键实现并解释，不能用“初始化完成”“验证通过”代替教学。先让读者理解并操作一组具体过程，再介绍批量自动化；入口若主要负责调用下层脚本，就简述调用关系，把篇幅留给实际完成工作的代码。同一操作中的调用、配置和检查应连贯讲述，不按函数或文件机械拆成多个章节；只展示理解当前过程所需的代码。对外只提供 note 中的 Humanize 写作子技能，不贴整个 note。内部同步、发布、审阅流程以及与读者使用无关的维护安排留在本 skill，不写进介绍文章；用户明确要求讨论维护机制时再展开。

配图说明只保留帮助读者理解或查证的信息，例如作者、论文名、图号和来源链接。直接引用原论文图时，不附加“从原 PDF 截取，未重绘”这类制作过程说明，也不例行补充“图中的 8K 是原图示例”。只有图中内容确实容易引起误解时，才在相关讲解中解释具体条件；截图方式和处理记录留在内部资料中。

技术讲解先给具体对象和一次实际的数据流，再引入术语。说明容器与组成部分、整体机制与其中组件的关系；对照原图时使用图中真实标签，并解释正文术语对应哪个范围。介绍方案贡献时，先说明前方案已经具备什么，再具体说明增加了哪些能力，不把工程封装写成新原理。用户的连续追问暴露出前置概念缺失时，回到正文补齐推导，不只在末尾追加问答。

必要细节的篇幅和层级服从文章主线。引入读者可能不熟悉的辅助工具或依赖时，在首次出现处就近解释它做什么、当前场景为何需要、与已有工具如何分工；例如安装命令下方用短段落或一个说明块补充。与主线关系较弱的细节，不因需要解释就单开章节，也不统一要求先讲一段工具原理再给命令。遇到“已经有 A，为什么还要 B”时，只补齐理解当前操作所需的区别、底层机制与替代条件，避免继续展开依赖的依赖。只有该问题本身构成本篇主要学习目标时，才独立成节。复读时同时检查两点：初学者能否理解每一步，以及补充解释是否打断或挤占了主线。

概念介绍应让读者在当前页面完成主要理解。展开论文时，把研究问题、具体输入与输出、方法的关键步骤、验证方式、贡献及适用边界讲清楚，按内容需要组织，不机械套标题。用例子补齐推导所需前提，解释影响理解的术语和分类；不能用“方法详见论文第几节”代替正文讲解。来源链接用于查证和深入阅读，理解当前论点不应依赖读者跳转到站外。

介绍研究工作时，先明确其主要类型：方法、模型、系统或框架、数据集、benchmark（评测基准）。Benchmark 要直接标明为 benchmark，围绕测试对象、题目、参考答案、判分与评测发现展开；区分评测端的检查机制和被测系统的运行机制，不把评测基准写成 Agent 设计方案，也不暗示它与训练方法构成技术替代或演进关系。跨类型比较时写明各自职责；从评测推导出的工程建议，应标明是应用层面的借鉴。

在本次笔记协作的每轮对话中，识别用户明确给出的、可复用的写作与内容取舍偏好，及时合并到本 skill 的相应位置。修正旧规则并去重，不积累聊天逐字稿，不把某篇文章的一次性要求扩大为通用规则。写作与复读直接在 note 内完成，不默认串联其他 Humanizer。

## 讲述式技术笔记

采用讲述式技术笔记语气：作者向读者讲述自己正在理解的问题，顺着问题解释概念和边界。有用户样稿时，以其表达习惯为准。

先整理原始材料中的问题、理解、证据和未解决处，再组织成文。以下指导适用于学习笔记与技术博客，不扩展成接口说明、故障报告或所有对话的通用风格。

- **作者与读者的位置。** 对话确实提供学习背景时，可以写“这是我系统学习……的笔记”，用“我”承接作者已有的疑问和判断，用“我们”邀请读者一起推敲。不要每段都用同一人称开头，也不要补造经历、感受或结论。
- **按理解的过程推进。** 从问题进入，解释原因，再引出概念、分类或边界。相邻段落之间说明关系，避免正文反复介绍文章定位、选材方法和分析流程。宏观与具体之间的承接要留下，不固定套用一种段落顺序。
- **让例子承接问题。** 引入例子前，先明确前文留下了哪个问题；例子应补充回答它所需的对象、条件或机制。不要因为沿用了前篇案例，就认为段落已有逻辑关系，也不要把“我们以……为例”当成固定的第二段。比较已有工具与新方案时，可以借例子说明原工具完成哪一步、其余工作由谁承担，再引出可复用的实现；这是一种推导方式，不是所有文章的固定结构。避免“全文沿用……”“本文采用……”这类编排说明，不能只靠人称、问号或连接词制造讲述感。
- **用已知解释未知。** 引入新概念时，选读者熟悉、理解它不依赖新概念的例子。讲 Agent，可以用压缩技术调研作为任务；不要在概念尚未介绍时，又用“调研 Agent 的记忆方案”解释 Agent。介绍到某个概念之后，可以举该概念内部的例子。
- **说明新增能力的来由。** 用已有方案引出新方案时，先说明已有方案在原场景中能解决什么，再说明目标或条件变化后留下的具体缺口，以及新方案怎样补上。区分替换原方案与在其上增加能力；需要某种能力，不等于必须采用某个具体工具。借用旧系统的经验时，只迁移成立的关系，保留类比的边界，不从表面相似推断能力相同。例子要参与推导，不能只在开头出现。
- **保留有用的过渡与连接词。** 句内和句间的目的、条件、因果与转折关系，应按语气自然表达，不为精简字数省掉让读者顺畅理解的连接词。比如“理解这套机制，可以先搭一个单节点 K8S”，在讲述式笔记中可写成“想要更直观地理解这套机制，我们可以先搭一个单节点 K8S”；偏正式的表达可用“为了观察这套机制的运行过程，我们先搭建一个单节点 K8S”。可选的理解或验证方法用“可以”，不要写成“需要”或“必须”。“从宏观上看”“具体到这里”“我们先看”等能说明话题推进的过渡也应保留。复读时检查关系是否表达自然；已经顺畅的句子无需补词，不连续套用同一句式，也不靠添加连接词掩盖推导缺口。删去只宣布“下面将介绍”的空句。
- **允许句子舒展。** 相关分句可以连在同一句里，让长短句随解释需要变化。不要按字数机械拆句，也不添加刻意的短句、金句或戏剧反问来制造人味。
- **把查阅过程留在正文之外。** 不用“本文依据某年某月某日查阅的资料”给技术讲解开场，文章日期和更新日期放在元信息中。只有时间或版本会改变能力、接口、维护状态或结论时，才在相关论点附近注明具体条件并附来源；不要删掉有实质意义的时效边界，也不要用查阅日期代替版本依据。
- **正文优先讲解。** 能用段落讲清的关系，不拆成字段清单。比较概念、参数、数据时可以用表格；步骤确有顺序时可以编号。去掉表格时，把其中有用的信息写回正文，不能借润色删掉技术条件。
- **整理口述，保留承接。** 用户样稿中的“嗯”、重复起头和语音转写错误默认整理掉，保留其语气与思路。用户要求保留语气词时照做；不要主动撒入“说实话”“其实吧”等口头填充。
- **按重要性说明不足。** 介绍产品、项目或方案时，围绕其价值、能力和用途展开，不必为了显得全面而主动罗列所有弱点。会明显影响使用体验、选择判断或当前结论的不足，应在相关位置说明；轻微且与当前主题无关的瑕疵，可以省略。这条叙述取舍原则也适用于学习笔记之外的成果介绍，不限于 Demo。省略不影响理解的细节时，仍应保持能力描述和效果承诺准确，不把未验证的效果写成已验证。

用户确认的语气样例：

> 设计 Agent，首先要明确它要完成什么，允许做什么，以及怎样检查结果。这是我系统学习 Agent 的第一篇笔记，我们先从这几个问题谈起。从宏观上看，设计一个 Agent 会涉及执行编排、记忆管理和工具调用，也会遇到多个 Agent 之间如何协作的问题。各个方面的具体实现和相关论文，我们留到后面的篇章里再展开。

样例用于校准作者视角、句子节奏和宏观到具体的承接，不是每篇都要复用的开头。不要机械添加第一人称、模仿相同句式或强制使用同一案例。

成文后先复核段落推进，再逐段检查表达。用一句内部说明指出：上一段留下什么问题，这一段补了什么，为什么接下来会讨论下一段。相同话题、同一个例子或“因此”等连接词都不能单独证明承接成立；若只能说“这里换个角度介绍”，就检查是否需要补前提、移动段落或删去它。尤其检查开头的问题是否真正引出了后面的例子与概念，不能只润色孤立句子。然后判断当前段落是在介绍事实，还是在作比较、因果解释或推导结论。单纯介绍且不影响主线理解的内容可以一句带过，不为每个术语补一段来历；一旦展开推导，就检查以下关系：

1. **结论由什么支持。** 找出本段实际要推出的结论、支持它的前提及中间关系，检查正文或前文是否已经交代。连接词和先后顺序本身不构成推导。引出新方案时，核对旧方案的能力、场景变化或未满足的需求，以及新增能力如何回应缺口。
2. **前提是否足够。** 前提合在一起应足以支持所写结论。不能把必要条件当充分条件，不能由结果反推某个可能原因，也不能把可行方案写成唯一必需方案。充分但非必要的条件可以支持结论，只是不能据此声称它是唯一途径。经验观察、相关性或类比若不足以形成必然推论，应保留适用条件并降低结论强度，不能为补齐推导而编造前提。
3. **省略是否影响成立。** 补齐会改变结论成立与否的前提、中间步骤和范围限制；不要求罗列所有可能结论或替代方案。只有对目标读者、当前上下文确实显而易见，且省略不会改变理解的步骤才可略去，不能把作者熟悉当成读者已知。拿不准时补最短的必要说明。
4. **展开是否必要。** 保留理解主线所需的推导，将辅助解释留在首次相关操作附近。删去重复前提、重复结论和无用的过程说明，不能为缩短文字删掉关键条件，也不能为形式完整强行增加章节。

这些问题用于写后检查，不作为正文的固定格式。可在内部用“前提仍成立，结论能否不成立”寻找反例；发现反例时，修正推理、补充有依据的条件或收窄结论，再复核相关段落。核对引用与不确定性，遵循用户最新明确的表达偏好；除非用户要求，不把逐段检查记录塞进文章。

## 同步公开的写作规则

本 skill 的“讲述式技术笔记”一节是公开 Humanize 子技能的规则来源。公开附件使用英文指令，写作对象仍是中文学习笔记与技术博客。英文译本保存在 `assets/oceanct-humanize-SKILL.md`，介绍文章保留中文。修改该节后，核对并更新英文译本，再更新 `scripts/sync_humanize.py` 的 `TRANSLATED_SOURCE_SHA256`（该节去掉首尾空白后 UTF-8 字节的 SHA-256）；脚本会拒绝从未复核的规则生成附件。同步安装目录与博客仓库中的 note 副本，再生成独立附件：

```bash
python3 /Users/oceanct/.codex/skills/note/scripts/sync_humanize.py --repo /Users/oceanct/projects/blog
```

用户确认公开 Humanize 规则的修改后，同步英文版本到 `/Users/oceanct/projects/oceanct-humanize`（`https://github.com/OceanCT/oceanct-humanize`），检查差异并提交、推送，核实远端版本。只发布已确认的规则，不把未审阅的博客文章一并发布。

## 确认后自动发布

发布前检查工作区差异与远端变动，明确当前源码分支和远端默认分支。默认把本次文章更新到远端默认源码分支；如果预览分支还包含未审阅的网站改版或其他修改，不把它们随笔记一并合入。将本次已确认内容单独整理到基于最新源码分支的工作区，保留用户其他修改。用户明确指定发布分支时按其要求执行。

只提交相关文件，不使用无选择的 `git add .`。仓库历史跟踪了 `node_modules`、`db.json` 和 `public`；避免提交依赖与缓存，已跟踪的构建输出按仓库约定处理。保留作者提交历史，不强推源码分支。

提交并推送已确认的源代码，从包含同一版本内容的干净发布工作区构建，再运行 `npm run deploy`（Hexo git deployer 输出到 `gh-pages`）。不要把其他本地未审阅笔记混入发布构建。检查推送和部署结果，并核实公开文章的标题及正文确为本次版本；若 GitHub Pages 尚未更新，报告“已推送，等待站点更新”，不能提前宣称上线完成。

认证失败时区分读取和写入：公开仓库克隆成功不能证明有推送权限。可使用 `git push --dry-run` 做不更新远端引用的写入预检，但它不能证明真正推送或部署一定成功。不要输出凭据，不在聊天中索取 token。若失败，保留成果并指出失败环节；凭据修复后继续既有发布授权，不再要求用户重审未变更内容。

交付状态明确区分“待审阅”“已确认但发布受阻”“已推送待站点更新”和“已上线”。待审阅时提供本地文章预览；上线后提供公开文章链接与简短检查结果。
