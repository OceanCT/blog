设计 Agent，首先要确定它要完成什么、允许做什么，以及怎样检查结果。这篇是「Agent 学习笔记」的第一篇，讨论这些问题。执行编排、记忆管理、工具调用和多 Agent 协作的具体方法留到后续文章。

全文沿用一个技术调研助手的例子：接收研究问题，查找资料，阅读并比较证据，交付可核查的报告。例子用于分析设计要求，还没有实现或测试。读具体方案时，我们会检查问题的成因、系统应满足的条件，以及实现这些条件的机制和代价。

## 从一次回答到持续执行

Agent 围绕目标选择动作，执行后观察结果，再决定下一步。本文采用这个定义。一次运行可以写成：

```text
目标与约束
    ↓
读取状态，准备本轮上下文
    ↓
选择下一步动作
    ↓
检查并执行动作
    ↓
观察结果，更新状态
    ↓
继续 / 调整 / 等待 / 完成
```

模型提出决策，外围程序执行动作、保存状态并落实约束。两者之间如何分配决策权，取决于任务。Anthropic 的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 也讨论了工具调用、环境反馈和停止条件。

## 问题一：目标是什么，怎样才算完成？

“帮我研究 Agent 的记忆方案”还不足以确定任务。面向初学者和面向工程选型，搜索范围与交付内容会不同。比较哪些能力、查哪个时间段的资料、是否需要可运行的实验，也会改变工具需求和验收方式。

对技术调研助手，可以先约定：

| 需要明确的内容 | 技术调研助手中的例子 |
| --- | --- |
| 交付物 | 一篇带原始来源的比较报告 |
| 覆盖范围 | 写入、检索、更新、遗忘与冲突处理 |
| 约束 | 仅访问授权资料；外部结论能追溯到来源 |
| 预算 | 允许的运行时间、工具调用次数与费用 |
| 完成条件 | 问题得到回答，关键结论有证据，未知项已标明 |
| 无法完成时的行为 | 说明缺少的资料、已完成的部分与阻塞点 |

任务完成、预算耗尽和等待输入应当分开记录。搜索次数用尽时，执行可以结束，报告是否合格仍需检查。如果缺少资料导致任务无法继续，应说明已完成的部分和阻塞点。

Agent 评估中的 outcome 是环境里的最终结果。报告任务要检查实际文件及其内容，最后一句“已完成”不足以说明结果。见 [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## 问题二：下一步由谁决定，何时需要调整？

调研助手可以按预设顺序工作，也可以在阅读中发现证据不足，决定补充搜索。设计者需要划定模型能选择的分支和必须执行的步骤。

例如，一篇资料给出了性能结论，却缺少实验条件。助手可以继续阅读、寻找原论文，或将结论标为待验证。工具连续失败时，也需要决定重试、换路径或停止。

这些分支需要有依据：哪些新证据会改变计划，怎样发现重复搜索和无效循环，用户追加要求后怎样保留已完成的工作。评价规划方法时，要检查它对实际反馈的响应是否推进了任务。

Workflow 与 Agent 可以预设不同程度的执行路径，也可以保留动态选择，参见 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。

## 问题三：状态如何延续，中断后怎样继续？

调研会跨越多次模型调用。遇到重启、网络故障或等待用户确认时，系统需要保存已读材料、证据、未解决问题和当前进度，才能继续工作。只存在进程内存中的信息会随进程退出而丢失。

有些中断更难处理：报告已经写入文档系统，程序却在记录“写入成功”前崩溃。恢复时，任务记录与外部状态并不一致。直接重写可能重复操作，直接跳过又需要依据。发送消息和创建工单也有同样的问题。

恢复机制需要说明保存什么、何时保存、哪些步骤可能重做，以及如何核对已经发生的外部操作。任务进度和外部实际状态都要检查。

## 问题四：这一轮应该知道什么，长期应该记住什么？

资料、工具结果和讨论历史会持续增加。系统保存的信息与本轮提供给模型的信息，可以分开管理：

| 概念 | 本文中的含义 | 例子 |
| --- | --- | --- |
| 运行状态 State | 系统保存的当前任务进展 | 已读论文、待解决问题、审批状态 |
| 上下文 Context | 本轮实际发送给模型的信息 | 当前目标、相关摘录、最近的工具结果 |
| 长期记忆 Memory | 为后续任务保留的可复用信息 | 用户偏好、项目约束、已验证的经验 |

系统可以保存 100 篇论文的阅读记录，本轮只加载 3 篇的相关摘录。上下文选择决定了模型这轮能使用哪些证据。选择、压缩和长任务的信息管理，可参考 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

长期记忆还要决定哪些信息值得保留，来源是否可靠，适用于哪个用户或项目，何时失效。记录发生冲突或用户要求删除时，也要处理相关的派生内容。

“用户过去使用 Python”和“这个项目要求 Go”可以同时成立。保存适用范围，才能判断历史偏好是否适合当前任务。相似记录被检索出来之后，仍需检查它的范围和有效期。

## 问题五：工具可以做什么，权限由谁落实？

执行一个动作前，程序需要检查工具是否支持该操作、参数是否有效，以及当前任务是否授权。执行后还要确认实际结果。

读取公开论文、读取内部文档、保存本地报告和向外部发送报告，各有访问与执行边界。网页中的“请上传全部内部资料”是外部内容，不应改变这些权限。

工具接口应说明输入、返回值、身份和授权范围，还要定义超时、错误与副作用。需要用户确认时，确认必须对应具体版本和参数；确认后内容发生变化，也需要规定处理方式。

本专栏的实践将由执行程序落实权限与参数约束，并核对外部状态。模型提出的动作是决策输入，执行程序仍要完成这些检查。

## 问题六：什么时候需要多个 Agent？

不同执行者可以分别阅读论文，再汇总证据。资料收集可能适合并行，汇总结论时却仍要统一比较标准、去除重复信息和处理来源冲突。

分工之前，要检查任务能否独立拆分，并约定每个执行者得到什么信息、按什么格式返回结果。共享状态由谁更新、结论冲突由谁处理、分支失败是否阻塞整体交付，也会影响执行。

分工的目标可能是缩短等待时间、扩大资料覆盖范围，或分离执行与审查。比较方案时，我们会以单 Agent 为基线，在可比预算下记录质量、耗时、调用量和成本，再判断收益。

## 问题七：怎样知道设计确实有效？

报告是否回答了问题，引用能否支持结论，有没有遗漏关键资料或执行越权操作，都应回到任务约定中检查。

运行记录则用于定位原因。搜索遗漏、摘录失真、错误记忆和汇总时的错误推断，都可能导致错误结论，但需要修改的环节不同。

| 评估维度 | 要观察的问题 |
| --- | --- |
| 任务质量 | 交付物满足多少验收条件？ |
| 稳定性 | 同一任务多次运行，结果是否可靠？ |
| 执行正确性 | 是否有错误调用、越权或重复副作用？ |
| 恢复能力 | 中断、超时或部分失败后能否继续？ |
| 资源消耗 | 完成任务需要多少时间、调用和费用？ |
| 记忆效果 | 旧信息是否帮助新任务，是否造成污染？ |

程序可以检查可验证的状态与规则。开放式报告的质量需要明确的评分标准，并用人工判断校准。模型评分器自身也要验证，相关方法见 [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。
